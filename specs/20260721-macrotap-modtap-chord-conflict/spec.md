# Spec: 双角色键 Mod-Tap——巨硬选字与和弦快捷键共存

## 1. 背景与问题

物理键盘模式下，底排"巨硬"槽位键（candidate2-5、翻页键）常常同时是和弦修饰键
（Sym / Fn / Alt_L / Alt_R / Shift_L / Shift_R）。用户（Titan2，tt2 预设）的实际配置：

- Alt = 5 号候选键，且是 Alt 双击锁定键，且是 `Alt+字母` 和弦前缀；
- Shift_L = 4 号候选键，且是 Shift 双击/长按锁大写的键；
- Sym / Fn 也同时占槽位并作为 `Sym+字母` / `Fn+字母` 快捷键前缀；
- 翻页键 = `Sym+O` / `Sym+P`（和弦形态）。

**最高优先级场景**（用户确认）：**翻页和弦与选字必须共存**——Sym 裸按选字、
Sym+O/P 翻页，两者都不能牺牲。

**既有语义（用户确认接受，本 feature 不改善）**：候选栏有候选时，Shift/Alt 的
双击锁定不触发（锁定让位给选字）——这两个键不存在"边选字边要锁"的真实场景。

**痛点**：裸按槽位键在 keyDown 瞬间立即派发选字。打字途中（候选栏有候选）想打
`按住 Sym + 字母` 这类快捷键时，Sym 按下那一下**先把候选字敲上屏**，必须等候选清空
后和弦才正常。用户日常高频困扰。

**现状基础**：代码库已有三套按键裁决状态机——符号键 tap-hold
（`HardwareChord.armSymbolTap` / `InputView.handleHardwareChordTapHold`，
"按下挂起、松手补发"，即 QMK Mod-Tap）、Shift 大写锁定（双击 300ms / 长按 500ms，
第一击延迟补发、被和弦使用则作废）、Alt 双击锁定（第一击放行选字、第二击消费锁定）。
**候选选字不在任何一套仲裁之内**——本 feature 就是补上这一环，把 tap-hold 泛化到
"双角色键"的选字角色上，并让三套既有机制与新挂起共存不冲突。

关联已知缺陷（不阻塞本 feature）：`docs/BACKLOG.md` B1——
`HardwareShortcutResolver` 的缓存失效监听器为弱引用匿名 lambda，GC 后改绑需重启
应用才生效。**决策（用户 2026-07-21）**：本 feature 不为 B1 做特殊绕开（避免
新增"特例逻辑"，且用户不想维护"这个开关即时生效、别的要重启"两套心智）；
B1 作为**紧随其后的下一个 feature** 统一修复，届时新开关自动受益。本 feature
真机验收期间，改配置后强停应用再测（临时纪律）。

## 2. 目标

- **G1（核心）**：双角色键（当前 candidate2-5 / 翻页键的**裸按绑定** ∩ 六个和弦
  修饰键之一）裸按时挂起选字；挂起期间按下"已绑定和弦键"（动作快捷键 + 翻页键）
  → 执行和弦、挂起作废；松手且无其它键 → 补发选字；按下未绑定和弦的其它键 →
  先补发选字、再正常处理该键。
- **G2（共存）**：Alt 双击锁定、Shift 双击/长按锁大写行为**与改动前完全一致**
  （含"有候选时让位选字"的既有语义）；被 latch 状态机消费的按键必须同时作废新
  挂起（防止"锁定成功、但松手时又补发了一次选字"）。
- **G3（可回退）**：设置新增总开关（默认开）；关闭后完全回到本 feature 之前的
  行为（裸按立即选字，和弦误触发原样）。

## 3. 非目标（明确不做的事）

- **不做**逐键开关（7~9 个开关无必要；默认值由"双角色"规则推出，不靠用户配置）。
- **不做**时间阈值/超时参数：裁决纯事件驱动（keyup / 下一个 keydown），无新调参项；
  长按任意时长后再按字母仍是和弦，不存在"挂起超时作废"。
- **不重写**三套既有 latch/tap-hold 状态机的内部逻辑，只新增"跳过/让位"规则。
- **不改善**"有候选时 Shift/Alt 双击锁定不触发"的既有语义（用户确认接受；
  如需改善另立 feature）。
- **不改**和弦匹配与优先级规则（动作 > 候选 > 翻页 的既有次序不变）。
- **不影响**单角色键（不含修饰键身份的槽位键，如空格 candidate1）与虚拟键盘模式
  （仅物理键盘模式的派发链改动）。
- **不动** `lib/` 下 fcitx5 C++ 层。
- 不修 B1 缓存 bug（单独 feature）。

## 4. 需求（用户视角）

- R1: 作为打字用户，我在候选栏有候选时按住底排修饰键再按字母，希望快捷键直接生效、
  不误敲候选字，以便流畅使用自定义快捷键。
- R2: 作为打字用户，我裸点底排键选字的手感不变（无感知延迟），以便选字速度不受影响。
- R3: 作为用户，我双击 Alt 锁 Alt、双击/长按 Shift 锁大写的老功能照常工作，以便
  既有习惯不被破坏。
- R4: 作为用户，我可以一个开关关闭新行为、退回旧手感，以便在新机制不符合预期时自救。

## 5. 验收标准（Acceptance Criteria）

> CI 只能验证编译；以下均为 `[真机]`（用户设备：Titan2 / tt2 预设），除非另注。

- [ ] AC1 `[真机]` 候选栏有候选时，`按住 Sym + 已绑定字母`（开关类动作）→ 动作执行，
      且**无任何候选字上屏**。
- [ ] AC2 `[真机]` 同 AC1，分别用 `Fn + 字母`（编辑类动作）、`按住 Alt + 已绑定字母`
      验证；Alt 场景同时确认 5 号候选未被敲上。
- [ ] AC3 `[真机]` 候选栏有候选时 `按住 Sym + O` / `按住 Sym + P` → 正常翻下一页/
      上一页，无候选字误上屏。**（最高优先级场景）**
- [ ] AC4 `[真机]` 候选栏有候选时裸点底排键（不接和弦）→ 选字正常，用户确认无
      感知延迟；空格（candidate1，单角色）行为与改动前完全一致。
- [ ] AC5 `[真机]` 回归（无候选干扰场景）：双击 Alt 锁定/解锁、双击/长按 Shift
      锁大写、锁定态直接打大写 → 全部与改动前一致。有候选时按 Alt/Shift 的锁定
      让位语义 → 与改动前一致（不改善也不恶化）；任何场景下不出现"锁定成功却又
      补发了一次选字"。
- [ ] AC6 `[真机]` 按住修饰键 ≥2 秒后再按已绑定字母 → 仍识别为和弦（验证无超时）。
- [ ] AC7 `[真机]` 挂起期间按下**未绑定和弦**的普通字母 → 先补发选字，随后该字母按
      现有修饰语义正常处理（如 Alt 未绑定 `Alt+x` 时，按 x 出的是 Alt+x 现有行为）。
- [ ] AC8 `[真机]` 长按双角色键触发系统自动重复（repeat 事件）→ 不重复选字、
      不重复触发任何动作。
- [ ] AC9 `[真机]` 关闭新开关 → AC1~AC3 的误触发行为**原样恢复**（旧手感），
      其余功能不变。
- [ ] AC10 回归：5 个预设（Q25 / BlackBerry / Titan2 / Titan2 Elite×2 / Passport）
      全平台 CI 构建全绿；虚拟键盘模式（软键盘）行为不变（编译级 + 用户抽查 `[真机]`）。

## 6. 约束与依赖

- **C1** 改动范围：`HardwareChord.kt`（挂起状态泛化）、`FcitxInputMethodService.kt`
  （物理模式派发链接入点，模式参照 `handleHardwareChordTapHold` 的既有位置）、
  `HardwareShortcutResolver.kt`（"和弦键命中表"：动作快捷键 + 翻页键；Alt-latch 同键
  二次按下规则）、`AppPrefs`（新开关）、设置页（开关行）。全部 Kotlin，不动 C++。
- **C2** 双角色键集合**动态计算**（随用户改绑/换预设自动跟随），不写死任何机型键位。
- **C3** 挂起的补发动作必须复用既有派发路径（按当时候选窗状态重评），不得另开一条
  选字通道；候选窗在挂起期间已关闭时，补发按"无候选"语义自然落空。
- **C4** 新开关走**普通偏好路径**（与其他键位配置一致），不做特殊缓存绕开；
  其"改后生效时机"与全局一致，由 B1 后续 feature 统一解决。
- **C5** 挂起只针对 keyDown（repeatCount==0）；repeat 与 keyUp 事件按 AC8 语义处理。

## 7. 开放问题（G1 前清零或标注接受风险）

- [x] Q1: 符号键（symbolPickerKey）双角色是否纳入？——**已覆盖**：既有
      `handleHardwareChordTapHold` 已做同样的挂起，本 feature 不重复处理。
- [x] Q2: 挂起补发时候选窗已消失怎么办？——**按 C3** 复用既有派发路径自然落空，
      无需特殊分支。
- [x] Q3: 设置项位置？——放「物理键盘」页（与候选键/翻页键配置同页，语义就近）。
- [x] Q4: 用户实测"Shift 锁大写无延迟"与代码 300ms 延迟补发描述不符——
      **接受风险**：v1 不改 caps 状态机内部；Shift 键一律遵循"已被既有状态机接管则
      跳过新挂起"，无论该状态机在用户设备上是否实际启用，行为都与改动前一致；
      由 AC5 真机回归兜底。
- [x] Q5: Shift/Alt 锁定与 Mod-Tap 是否需要深度合并？——**不需要**（用户 2026-07-21
      确认）：有候选时锁定让位选字是既有语义且可接受；v1 只需保证 latch 消费时
      作废挂起、行为与改动前逐场景一致。
